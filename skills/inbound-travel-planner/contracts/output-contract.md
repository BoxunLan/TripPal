# 输出契约（Output Contract）

> 本文件定义**所有**入境游攻略的强制产出格式。任何工作流（W1–W8）生成的内容，
> 最终都必须收敛到这一套结构，否则视为不合格。

---

## 一、五段式骨架（硬约束）

```markdown
# {编号} {问题原文}

## 需求理解
（见 §二）

## 完整攻略
（见 §三，内部结构由具体工作流决定）

## 信息覆盖自查表
（见 §四，12 行固定模块）

## 需实时检索确认的事项
（见 §五）

## 缺失项与需追问用户的信息
（见 §六）
```

> 说明：单篇产出可省略"编号"（直接以问题原文作标题）。批量产出须带编号，
> 并额外生成 `00_总索引.md`（编号 / 主题 / 文件名 / 状态）与
> `99_覆盖分析表.md`（逐篇模块覆盖与缺口汇总）。

---

## 二、`需求理解` 写法规范

固定 4 件事，用 2–4 段自然语言写，不用列表：

1. **目标读者画像**：国籍/语言、是否首次来华、是否懂中文、持什么卡、有无中国手机号。
2. **核心诉求**：用户真正想解决的问题（不是"了解 X"，而是"怎么做到 X"）。
3. **关键难点**：3–5 条这一场景特有的坑（用"第一……第二……第三……"排列）。
4. **写作立场**：明确声明——不假设用户会中文/有中国手机号/会用中国 App；
   所有时效数字标"需实时检索确认"，不编造。

> 允许在末尾附 3–5 条"目标读者/核心问题/关键难点/写作立场"的短列表（部分篇章这么做，
> 属可选增强，不是必需）。

---

## 三、`完整攻略` 写法规范

内部标题层级用 `### 一、二、三……`（中文序号）或 `### 第一步、第二步……`，
**具体选用哪种由工作流决定**（见下）。硬性要求：

- **每一步都可执行**：动词开头，给出"第一步做什么、第二步怎么买票、第三步如何沟通"。
- **给兜底方案**：每个高风险环节必须给"最差情况怎么办"（找酒店前台 / 找游客中心 / 用现金 / 用翻译 App 截图）。
- **用表格承载可对比信息**：票价档位、渠道对比、场景可用性等，一律用 Markdown 表格。
- **分人群/分档位**：预算、体力、经验不同的用户，给差异化建议。
- **不编造时效数字**：票价、时刻、名单、开放时间、放票时间——只给"方法 + 渠道"。

各工作流的内部骨架：

| 工作流 | `完整攻略` 内部结构 |
|---|---|
| W1 单城 | 行前必做 → 抵达交通 → 住宿选址 → **逐日行程（Day 1…Day N）** → 市内交通支付 → 餐饮 → 安全 → 预算表 → 检查清单 → 文化礼仪 |
| W2 跨城 | 线路总览 → 城际大交通 → **逐段：城市 A（Day 1–x）→ 城市 B（Day x–y）…** → 衔接细节 → 住宿 → 预算 → 清单 |
| W3 主题 | 主题总览（这条线在讲什么）→ 主题特别提醒 → **逐段：主题模块 1 → 模块 2 …** → 主题清单（必吃/必看/必体验）→ 预算 → 清单 |
| W4 人群 | 为什么选这条线 → 落地第一天 90 分钟 → 行前必做 → 逐日行程 → 人群专属章节（医疗/无障碍/饮食/安全）→ 预算 → 清单 → 高频话术 |
| W5 实务 | **第一步 → 第二步 → … 第 N 步**（编号步骤流）→ 常见错误与失败应对 → 检查清单 |
| W6 约束 | 先讲清约束边界 → 为什么选这条线 → 逐日行程 → 约束下的支付/住宿/餐饮降本 → 省钱 vs 升级开关 → 清单 |
| W7 特殊 | 先判断"你属于哪种情况"（决策树）→ 按类型分述 → 完整时间轴 → 常见坑 → 应急 → 清单 |
| W8 对比 | 先给一句话结论 → 总对比表 → 分维度展开 → 分人群建议 → 混合/组合策略 → 避坑 |

## 四、`信息覆盖自查表` 规范（12 行固定模块）

**逐行填写，不得空行。** "是否覆盖"列取值：`是` / `中` / `弱` / `否` / `不适用`。
"完整度"列取值：`高` / `中` / `低`。备注列写一句实话（弱在哪、为何不适用）。

| 模块 | 是否覆盖 | 完整度 | 备注 |
|---|---|---|---|
| 签证/免签 | | | |
| 入境准备 | | | |
| 外卡支付与支付宝/微信绑定 | | | |
| 手机卡/上网 | | | |
| 语言翻译 | | | |
| 住宿登记 | | | |
| 高铁/飞机购票证件 | | | |
| 景点预约证件 | | | |
| 餐饮英文服务 | | | |
| 安全应急 | | | |
| 预算拆解 | | | |
| 步行强度 | | | |

> 判定原则：**不要为了凑"是"而硬写**。单城攻略里"高铁购票"可以诚实地写"中/弱"；
> 度假海岛攻略里"景点预约"可以写"不适用"。诚实的弱覆盖比虚假的全覆盖更有价值。

## 五、`需实时检索确认的事项` 规范

每条用统一三元组格式：

```
- 事项：{具体要确认的东西}
  | 为什么需要确认：{为什么它易变/时效强}
  | 建议渠道：{官方渠道名}
```

要求：一般列 6–8 条；覆盖本篇涉及的所有时效敏感点（政策、票价、时刻、放票、名单、开放季）。

---

## 六、`缺失项与需追问用户的信息` 规范

列出"要让攻略从泛化变成精准，必须知道但用户还没给的信息"，每条用：

```
- {要问的信息}：{它会影响什么决策}
```

要求：一般 5–7 条。典型维度：国籍/护照类型、出行月份、同行人构成、预算上限、
抵离城市、饮食禁忌、体力/无障碍需求、兴趣深度。

> 这一节是 Skill 的"诚实边界"——它承认攻略无法一次到位，把不确定交还给用户。

---

## 七、标注纪律（贯穿全文）

- 每条关键事实/建议后缀 `[通用知识]`（稳定常识）或 `[需实时检索确认]`（时效信息）。
- 一句话里既有常识又有时效点时，拆开或把标签放在对应分句后。
- 表格里的时效单元格，在单元格内标 `[需实时检索确认]`。
- 判断标准：**"如果这条信息今天对、半年后可能错"→ 必须标"需实时检索确认"。**

- [ ] 每个高风险环节都有兜底方案

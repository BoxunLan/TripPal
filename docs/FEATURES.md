# TripPal 功能说明（现行版）

面向**接手者 / 评审者 / 融合方**：这份文档讲「现在这个服务能做什么、怎么做的、边界在哪」。
接口字段级契约见 `docs/API.md`；**要把某块功能拿去融合的看 `docs/MODULES.md`**；内部结构与闭环设计见 `docs/ARCHITECTURE.md`；技能进化闭环见 `docs/SKILL_LOOP.md`。

> 一句话定位：**给来中国旅游的外国人用的中文行程与事实助手** —— 能排行程、能答会变的事实、
> 能答不会变的常识，答不了就明说答不了，而不是编一个像答案的句子。

## 1. 服务形态与入口

FastAPI 单服务，默认 `http://127.0.0.1:8000`。共 **7 个端点**，但只有 2 个进 OpenAPI 契约
（其余 5 个是给自家前端用的，标了 `include_in_schema=False`，接口可用但不在契约里）：

| 端点 | 方法 | 进 OpenAPI | 作用 |
|---|---|---|---|
| `/health` | GET | ✅ | 健康检查：后端类型、知识库条数、embedding 维度、路由/检索/分类器版本 |
| `/plan` | POST | ✅ | **主入口**。一句话进去，六种响应形态之一出来（同步） |
| `/session/{id}` | GET | ❌ | 读会话已确认槽位（前端用来回填「行程信息卡」） |
| `/plan/start` | POST | ❌ | 起一个后台任务，立刻返回 `task_id`（长行程不占连接） |
| `/plan/progress/{id}` | GET | ❌ | 轮询上面的任务：已完成阶段 + 耗时 + 最终响应体 |
| `/plan/stream` | POST | ❌ | NDJSON 流式：每个节点跑完就吐一行 |
| `/` | GET | ❌ | Web 对话界面（`web/index.html`，服务端直接吐） |

**融合两条路径**（细节见 `docs/API.md`）：
① 跨进程 HTTP（`/plan`、`/plan/stream`、`/plan/start`+轮询）；
② 同进程内嵌（`host.mount("/travel", create_app(deps))`，或直接 `build_graph(deps).invoke(...)`）。

⚠️ **状态在进程内**（会话记忆、任务表都只在当前 worker 的内存里）。`--workers > 1` 会让会话与
轮询漂移；要横向扩就得先把这两处换成共享存储。

## 2. 六种响应形态

一句话进来，出去的**永远是这六种之一**（`type` 字段）。形态本身是产品设计的一部分 ——
它决定用户看到的是「行程」「事实」「常识」「追问」还是「答不了」。

| `type` | 什么时候出 | 关键字段 |
|---|---|---|
| `clarify` | 关键槽位缺（目的地/天数/预算/同行人） | `question`、`missing_slots`（只问第一项，不四连问） |
| `plan` | 信息够了 → 排行程 | `itinerary`、`route`、`citations`、`validation`、`checklist` |
| `realtime` | 问**会变**的事实（政策/开放时间/时刻/天气/交通） | `found`、`channels`（权威入口）、`unverified`、`expired_dropped` |
| `answer` | 问**不会变**的常识（「西湖有多大」） | `answer`、`confidence`、`hits`（相关条目）、`verify`（复核入口） |
| `guide` | 寒暄 / 致谢 / 元问题（「你好」「你是谁」） | `reply`、`starters` |
| `degraded` | 校验没过且回炉一次仍没过 | `reason`、`partial`、`validation` |

⚠️ **异常不抛 500**：链路内部出错会退化成 `200 + type=degraded`，调用方**必须判 `type`**，
不能只看 HTTP 状态码。

## 3. 前门怎么分流

不是所有话都该去排行程。「你好」被要求填四问、「西湖多大」被反问预算，都是方向性错误。
现在的分法是**先分类、再决定走哪条路**：

```
一句话
 ├── 寒暄 / 致谢 / 元问题 ──────→ guide      （不检索、不追问）
 ├── 会变的实时事实 ────────────→ realtime   （旁路，毫秒级，不经 LLM 生成）
 ├── 不会变的常识 ──────────────→ knowledge  （旁路，可给通用常识但必须标注未核实）
 └── 其余（排行程）────────────→ classify → route → retrieve → generate → validate
```

三条旁路**完全绕开** `classify/route/retrieve/generate/validate`：这也是为什么实时事实能毫秒级
返回（实测 0.0s），而排行程要几十秒到几分钟。

## 4. 知识库

- **规模**：170 条（`seed/*.jsonl`）。分文件：`general` 72 · `scene_roadtrip` 22 · `scene_visa` 22 ·
  `realtime` 21 · `scene_budget` 17 · `scene_family` 16。
- **三层**：`general`（普适知识）／`scene`（场景知识：family/budget/roadtrip/visa）／
  `realtime`（会变的事实，带生效日与有效期）。
- **四个场景**：`family`、`budget`、`roadtrip`、`visa`；`general` 是兜底，不是第五个场景。
- **作用域 + 地理过滤**：检索按 `knowledge_scopes`（`general` / `scene:X` / `realtime:X`）取层，
  再按目的地做地理过滤；目的地词典没覆盖时**放开地理过滤**（否则整条链路只能输出「待核实」）。
- **层配额**：不同场景给不同层不同名额（如 visa 场景 `realtime` 占 0.6，family 占 0.3）。
- **本地开发无需 docker**：`TRAVEL_VECTOR_BACKEND=memory` 走内存向量库；生产用 pgvector。

## 5. 时效性（本轮重点核查 + 修复）

知识库里**有大量会过期的内容** —— 门票价、开放时间、签证政策、节假日安排、价格带。
所以每条条目有三个时间字段，缺了就不该被当成现行口径使用：

| 字段 | 含义 | 谁用 |
|---|---|---|
| `effective_date` | 这条信息的**生效日** | 政策类必须有；回答「这条是不是现行」要靠它 |
| `fresh_until` | **有效期至**（过期即不可用） | 时效闸门 |
| `source` / `source_url` | 来源名称 / 官方入口 | 用户自己复核 |

**当前状态**：170 条**全部**带 `fresh_until`（集中在 2027-03-31 共 100 条、2027-06-30 共 68 条），
其中 1 条已过期（`rt-th-stale-001`，2025-06-30 —— 是**故意留的闸门测试样本**），1 条为 2026-12-31。
另 33 条带 `effective_date`（政策类必须有）。

### 本轮修的缺口

原实现**只对 `realtime` 层设过期闸门**（`app/retrieve.py`），理由是「常识不会过期」——
但这是错的：`general` / `scene` 层里同样有票价、开放时间、预约规则。过期条目照样被召回，
等于**拿旧价签答今天的问题，而用户看不出它已经过期**。

现在：**任何层**只要 `fresh_until < 今天` 一律丢弃、不参与排序、不进上下文；丢弃条数记进
`dropped_stale`（plan 链路）与 `expired_dropped`（realtime 链路），闸门不静默。
代价说清楚：宁可这一条不进上下文（生成会退化成「待核实」），也不给一个看起来确定、实际陈旧的值。

回归测试：`tests/test_guards.py::test_stale_chunk_of_any_layer_never_reaches_the_context`。

## 6. 相关条目的网址（本轮重点）

### 链路本来是通的，断在两处

用户能看到「相关条目」的地方有三处（行程卡引用、实时卡已核实、常识卡相关条目），
三处**共用同一个 `chip()` 渲染**：有链接就渲染成 `<a href target="_blank">`。

**断点 ①（前端 bug，已修）**：行程卡的 `citations` 字段名是 `source_url`，
而 `chip()` 只读 `c.url` —— 于是**行程里所有引用 chip 都点不动**。
实时卡与常识卡恰好手写了 `url:` 映射，才显得正常（同一份数据、两种字段名，最坑的一种不一致）。

**断点 ②（数据缺口，已补）**：知识库里多数条目**根本没有网址字段**。

### `source_url` 的语义（重要）

它**不保证是这条信息的原始出处**，而是「**点得开的官方核实入口**」：

- 条目来源本身是官方文件（如「国家移民管理局 2026-08-20 公告」）→ 链接就是那个官方站点；
- 条目是**编辑整理**（source 写着「…整理 / …摘录」，没有单一原文页）→ 链接指向**该主题的官方入口**
  （天气 → 中国气象局，景区预约 → 文化和旅游部，铁路 → 12306，维权 → 12315 平台……）。

为此前端把两种状态**做成看得出区别**：
带 ↗ 的强调色 chip = 可点的官方入口；虚线压暗 chip = 编辑整理条目，hover 明说「无官方入口可点」。
不这么分，用户点一下没反应，只会以为坏了。

**覆盖情况（本轮）**：带官方入口的条目 **42 → 62 / 170**；
来华条目 **31 → 51 / 99**。新增的每一个 URL 都是**先探测可达再写入**，不臆造。

回归测试：`tests/test_source_links.py`（数据形状 + 覆盖率下限 + 钉死若干条 + 前端契约）。

## 7. 按来源国做中外类比

外国游客看不懂中国的「做法」，但看得懂「和他自己国家比差在哪」。所以引入**用户来源国**，
并且**两条回答链路都接上了类比**：

- **`nationality` ≠ `destination_country`**：前者是「游客本人来自哪」（德国），后者是
  「要去/要办签证的国家」（中国）。两者混掉，检索就会去捞出境知识 —— 这是历史漏点的形状。
- **抽取**：只认明确身份措辞（「我是德国人」「I'm from France」「as a Spanish traveller」），
  **裸地名词不认**（「我是上海人」「北京离上海多远」都必须抽不出来）。抽不到就不写 ——
  不猜，猜错整篇类比跑偏。
- **表单直填**：行程信息卡新增「来自（国家）」，填了直接落槽位（不经抽取），
  用宽松匹配（`United States` → 美国）；表里没有的国名也照收，丢掉的代价是类比全没了。
- **记性**：来源国一经说出就落会话槽位 —— 包括**常识旁路**（它不经过行程那条槽位合并，
  所以在 `knowledge_node` 里补写）。否则「我是德国人，怎么点菜」之后的每一句追问都要
  重新自我介绍一遍，类比也跟着断。优先级与槽位一致：**本句 > 会话历史**。

### 两条链路各自的规则

| 链路 | 谁在走 | 规则位置 | 要求 |
|---|---|---|---|
| 行程生成 | 「排个 5 天行程」 | `prompts/base.md` 第 11 条 | 至少 1–2 处类比，写进活动的 `detail` / `notes`；**饮食/文化/礼仪/习俗/节日类给 2–3 处** |
| 常识作答 | 「这里要给小费吗」「川菜是不是都很辣」 | `prompts/answer.md` 第 5 条 | 文化/饮食类**必须**给 1–2 处；其余话题有可比点就给 1 处 |

- **素材可以来自常识，不必来自知识库** —— 类比讲的是「同 / 不同」这层关系，不是精确事实，
  所以知识库里没有对应条目时**照样类比**。这一句必须显式写进提示词：不写，模型会因为
  「没有 `citation_key` 可引」而整段放弃类比（退化成一句干巴巴的「按这里的来」）。
- **话题类型是确定性判定的**（`app/knowledge.py::culture_food_topic`，词面匹配、不调模型）：
  文化 / 饮食 / 生活习俗类 → 提示词把类比标成**必须**；其余 → 「有可比点就给 1 处，不必硬凑」。
  判宽是刻意的 —— 命中的代价只是多问一句要不要类比，判漏的代价才是该类比的话题一个字没提。
- **刹车（两条链路都带）**：
  - 类比的只有**框架**（同/不同这层关系：小费、几点吃饭、排队与预约、能不能用本地卡、
    水要不要烧开、进寺观要不要脱鞋、送礼收不收）；
  - **绝不编造对方国家的具体规定、数字、价格或法律**（宁可只说「在中国是 Z」并提醒「按这里的来」）；
  - **类比不豁免「事实可溯源」**：由类比带出的具体数字（时间 / 价格 / 时长）仍然需要
    `citation_key`，没有就写「待核实」；
  - 来源国缺失时**不做类比**（不写「如果你是美国人……」这种假想句式）。

回归测试：`tests/test_nationality.py`（正/负例抽取、与目的地国分离、表单规范化、两条链路的
提示词注入与刹车、话题判定、常识旁路透传与记忆）。

## 8. 槽位与「行程信息卡」

- **槽位**：`destination` / `destination_country` / `days` / `date_range` / `start_date` /
  `budget`（`daily_budget`、`budget_basis`）/ `party`（`party_size`、`has_children`、
  `child_age`、`has_elder`）/ `pace` / `interests` / `constraints` / `multi_city` / `nationality` …
- **优先级**：**本句 > 表单 > 会话历史**。本句最新最明确；表单次之；会话里的最旧。
- **「行程信息卡」的存在理由**：口语的写法**枚举不完**。同一个意思可以说成
  「只有我一个人 / 就我一个成年人 / 我自己 / 1 位成人」，正则补一轮漏一轮。
  表单是那条**确定能通**的路：填了就直接是槽位，不经抽取、不靠识别。
  同行人四项**全留空 = 没填**（不会被伪装成「已知 2 人」）。
- **多城**：`multi_city` 记全部站点，`destination` 仍是首站；支持「把上海换成杭州」这类换站。

## 9. 多语言

支持 `zh`（默认）/ `en` / `ja` / `ko`。三条边界（改动前必读）：

1. **检索语言恒为中文** —— 知识库是中文语料，`rewritten_query` 必须始终中文；
   跟着用户语言走，英文请求的召回会直接崩。
2. **输出语言跟用户** —— 但 `citation_key`、来源原文、日期、金额**保持原样**（翻译了引用就断链）。
3. **开发期文案恒为中文** —— findings、日志、报错、测试断言不随语言变化。

语言判定是**确定性**的（按字符集：假名 → ja，谚文 → ko，汉字 → zh，其余 → en），不调模型。

## 10. 校验、降级与工具

- **校验节点 + 回炉**：生成后过一遍校验（事实可溯源、预算闭合、硬约束落实等）；
  未通过则**回炉一次**（`max_repair_rounds=1`），再不过就出 `degraded` 并把未解决项列出来。
- **事实必须可溯源**：凡是开放时间/门票/签证材料/交通耗时这类具体事实，必须带
  `citation_key`；找不到凭据就写「待核实」，**不编造**。
- **工具**（白名单，仅三个）：`budget_sum`（算术，在 validate 阶段跑）、
  `opening_hours`、`visa_policy`。白名单外的调用一律拒绝并留失败记录。

## 12. 已知边界 / 待办

- **进程内状态**：会话与任务表不跨 worker，横向扩需换共享存储。
- **融合形态未定**：跨进程 HTTP 还是同进程内嵌、会话 id 谁生成、是否多副本、鉴权层级、
  输出语言策略、批量/异步回调 —— 见 `docs/API.md` §9 待确认清单。
- **`source_url` 覆盖仍有缺口**：99 条来华条目里还有 48 条没有官方入口，因为它们是

# skill 进化闭环（设计稿）

> 一句话：**从真实用户数据出题，在真实执行轨迹里「训练」skill，配对评估决定留下什么。**
>
> 这份文档和 `ARCHITECTURE.md` 平级：那个说「系统怎么跑」，这个说「**skill 怎么变好**」。
> 改 skill 之前先读 §1（三条被实测修正的假设）与 §2（三个承重关节），
> 那两节里的每一条都有出处，不是设计偏好。

---

## 0. 闭环长什么样

```
① 采集   真实浏览器使用数据 → 高频需求场景
② 出题   场景 → 任务卡（含「期望终态」，必须可确定性判分）
③ 基线   干净上下文的执行 agent，**无 skill** 跑一遍 → 写 log.md（轨迹）
④ 判分   成败 + **归因四分类**（承重点 B）
⑤ 写/剪  optimizer agent 出 skill 稿 → 人类评审过闸
⑥ 复跑   带 skill 跑同一批任务 → 新 log.md → 回到 ④ 做配对对比
                 └────────── 回到 ④ ──────────┘
```

四道闸：**G1 任务合法性**（可判分？没泄漏答案？）· **G2 配对评估**（同任务 ±skill，只留 skill 这一个变量）·
**G3 回归门**（held-out 上不许掉分）· **G4 剪枝**（加了必须能删）。

承重点 **A**（谁判成败）在 ③→④ 之间，**B**（失败归因）在 ④，**C**（剪枝 + 回归门）在 ⑤→⑥。

## 1. 三条被实测修正的假设

你那套叙述里,**方向是对的,但有三处量级/顺序需要改**。都有出处。

| # | 直觉 | 实测结论 | 出处 |
|---|---|---|---|
| 1 | optimizer agent 分析 log 就能产出好 skill | **模型自产 skill 的平均增益 = 0。** 87 个任务 / 18 个 model-harness 配置下，**人工策展** skill 把通过率从 33.9% → 50.5%（**+16.6pp**），而**自产** skill **加不了分**。<br>但反过来，**有真实轨迹语料**的 agent 做**语料级统计式反思**，单次离线 pass 就胜 GEPA（3/4 基准）与 SkillOpt（4/4），+16.6pp，成本约 **$1.60**、比搜索式便宜 **22×**。 | SkillsBench `arXiv:2602.12670`；CASD `arXiv:2609.26261` |
| 2 | 有了 seed skill 再跑一轮、再优化，循环迭代 | **迭代搜索这件事本身可以不必要。** 差别在**反思范围**：是「对着小批轨迹逐步推理」，还是「写分析代码算**语料级统计**、找出系统性失败模式」。后者一次就够。<br>→ 所以**第二轮的真正价值不是「涨分」，是「查回归」**（见第 3 条）。 | CASD |
| 3 | 失败的任务 → skill 里**重点做约束** | **加约束会掉分。** 聚焦型 skill（≤3 个模块）**+18.9pp**，全面型（覆盖每个 edge case）**+5.7pp** —— 差近 4 倍；**85 个任务里有 24 个变差**。<br>→ 必须补**剪枝 + 回归门**，否则 skill 会单调膨胀，越加越差。 | SkillsBench |
| 4 | 成功的任务 → skill 可不涉及 | **这条方向是对的**：增益集中在预训练数据稀缺的领域（医疗 **+51.9pp**、制造 **+41.9pp**），本行规强的领域增益小（软工 **+4.5pp**、数学 **+6.0pp**）。<br>→ 但「成功」必须按**多次 rollout 的通过率**算，不能按单次成败（理由见 §2-A）。 | SkillsBench |

**一句话归纳**：你这个环成立，是因为**它带了真实轨迹**（避开了 SkillsBench 里「让模型凭空自产 skill」那个 +0 的坑）。
但**「optimizer 自动写 skill」这一步不能全自动** —— 人工洞见才是瓶颈。

## 2. 三个承重关节（现在是空的）

### A. 谁判成败 —— 单次成败没有信息量

这是整个环的分水岭。三种做法，只有第三种能支撑结论：

| 做法 | 问题 |
|---|---|
| optimizer 自己看一眼觉得「这次答得不错」 | 自评偏差；同一模型族的盲区是**相关**的，所以「看起来挺好」会系统性地骗过自己 |
| 单次 rollout 定成败 | **采集噪声**。本项目已实测：`ecnu-plus` 分类同一句「我们三个人去厦门 5 天，预算 8000」两次分别落在 `general` 与 `budget`。一次成功不代表「知识足够」，可能只是这次采样对了 |
| ✅ **确定性 verifier + 多次 rollout 取通过率** | SkillsBench 全程用 pytest 断言、**明确不用 LLM-as-judge**，理由正是「LLM 打分可能奖励看起来更漂亮的输出」。ClawBench 用 Agent-as-Judge 兜底，但它在人工审计子集上的 raw agreement 是 **84.97%–93.46%** —— 也就是说**约 1/10 的判断是错的**，所以它只配当兜底、不能当主判 |

**定死的口径**：
1. **主判必须是确定性的**（能写成断言的东西就写成断言）；
2. 每条任务跑 **≥3 次**，记 `pass^k`，不记单次；
3. LLM judge 只用于「过程合规性」这类无法断言的维度，且**必须在人工抽查过的一致率上报数**；
4. 「成功」的定义要写进任务卡，不能事后解释。

### B. 失败归因四分类 —— 只有一支属于 skill

这是最容易被跳过、也最致命的一步。见 §5 的判定表。

要点：**把失败轨迹直接丢给 optimizer，它会为每一类失败都写一条规则**，而其中有 3/4 类写了毫无用处甚至有害。
本项目自己就有三个现成反例（天安门被追问 / 西湖不给答案 / 来源链接跳首页）—— **全是代码与配置缺陷**。
当时若把这些轨迹喂给 optimizer，它会写出「遇到事实问询要分流进旁路」这类 skill 规则；
而真正的修法在 `app/graph.py` 与 `routes.yaml` —— 写进 skill 一个字都没用。

### C. 剪枝 + 回归门 —— 加规则的人永远比删规则的人多

由 §1 第 3 条，这不是洁癖，是**分数问题**。需要三件东西：

| 机制 | 做什么 | 借谁的做法 |
|---|---|---|
| 语义去重 | 新规则是不是已有规则的改写？ | EvolveR 的 experience base management |
| 效用打分 | 每条规则被引用次数 × 对成功结果的贡献 | 同上（其「Ideal 原则」占比在最高分档从 **26% → 82%**） |
| 剪枝 | 低分规则定期删；**删规则与加规则同一优先级** | 同上 |
| 回归门 | 在 **held-out 任务集**上跑，掉分就回滚 | SkillsBench 的配对评估 |

## 3. 角色

| 角色 | 输入 | 输出 | 关键约束 |
|---|---|---|---|
| **调研 agent** | 真实浏览器数据 | 高频场景清单 | 只报「用户**做了什么**」，不推断「用户**应该**做什么」（见 §8 隐私与偏差） |
| **出题 agent** | 场景清单 | 任务卡（含期望终态 + verifier） | 任务卡**不得引用任何 skill 的名字**；不得把答案写进题面（SkillsBench 的 leakage control） |
| **执行 agent** | 任务卡 | `log.md` | **上下文干净**；执行时不加载待评估的 skill；不许看别人的轨迹 |
| **判分 agent** | 轨迹 + verifier | 通过率 + 证据 | 优先跑确定性断言；LLM judge 只兜底 |
| **optimizer agent** | 一批轨迹 + 通过率 + 归因表 | skill 稿（含**删除建议**） | 必须**同时**给出「加什么」与「删什么」；只允许 ≤3 个模块 |
| **人类评审** | optimizer 的稿 | 通过 / 打回 | **不可省** —— §1 第 1 条：模型自产 skill 平均 +0，人工洞见是瓶颈 |

## 4. 轨迹契约：`log.md` 要记什么

ClawBench 的实践是**同步录五层**：会话视频 / 逐步截图 / HTTP 流量 / agent 消息 / 浏览器动作。
本项目轻量版照这个骨架砍：

```
evals/runs/<task_id>/<run_n>/
  task.json        任务卡快照（含 verifier 与期望终态）
  log.md           人读的轨迹（下表的行）
  trace.jsonl      机器读的同内容
  verdict.json     判分结果 + 证据 + pass/fail + 归因标签
  artifacts/       截图 / 响应体 / 生成的 HTML
```

`log.md` 每步一行：

| 字段 | 说明 |
|---|---|
| `step` | 序号 |
| `action` | 做了什么（哪个端点 / 哪个页面 / 哪个命令） |
| `observation` | 观测到什么（截断后的返回体、DOM 状态、报错） |
| `think` | 当时的判断（**这是最有价值的一列**：失败往往在 think 里就注定了） |
| `cost` | 耗时 / token |
| `artifact` | 落盘的证据文件 |

**一条硬规矩**：**必须记「没做什么」** —— 跳过的步骤、放弃的路径、超时、`found=0`。
失败信号经常是沉默的：Agent 没报错、没放弃，只是**选择了一条省事的错路**。
轨迹里只记「做了什么」的话，这类失败在 log 里是隐形的。

## 5. 失败归因判定表（承重点 B 的落地）

对每条失败轨迹按顺序问三个问题，命中即停：

| 顺序 | 问题 | 判据（怎么看出来） | 归因 | 该改什么 | skill 有用吗 |
|---|---|---|---|---|---|
| 1 | 期望的那条事实，**数据里有吗**？ | 直接查 `seed/*.jsonl` / 工具返回；数据里根本没有 → 全怪模型是错的 | **数据缺** | 补 `seed/*.jsonl`、补工具、补 `routes.yaml` | ✗ 完全无效 |
| 2 | 模型**知道该做哪一步动作吗**？ | 轨迹里**没有**任何试图做对动作的痕迹（它没去查、没去抽槽、没想到要分流） | **知识缺** | ✅ 写 skill：流程、检查项、反例 | ✅ **唯一的一支** |
| 3 | 动作做了，**结果还是错的**？ | 用了对的工具/流程，但算错、抽错、格式错、超预算 | **能力缺** | 改代码（确定性逻辑不该交给模型）、拆小任务、换模型 | ✗ 最多当护栏，别指望它修 |
| 4 | 以上都不是 | 题面有歧义 / 期望终态定义不清 / 判分本身不稳 | **任务有病** | **退回出题 agent 重出题**；这条轨迹作废，不计入统计 | ✗ |

**本项目当前的先验**（跑完 S1 会用真实数据替换掉）：
`seed/` 共 **170 条**，目的地集中在 **中国（厦门 / 成都 / 大理 / 青岛 / 云南 / 四川）/ 泰国清迈 / 北京 / 上海**，
另有美国 / 新西兰 / 澳大利亚 / 申根区等路线与签证场景，以及**外国人来华政策**；
其余目的地只有 general 层垫底（出境日本内容已于 2026-10-05 整块移除）。
所以「鼓浪屿今天开放吗」「西湖有多大」这类问题，**大概率落在第 1 行（数据缺）**，
而不是第 2 行。**先归因再写 skill**，否则第一版 skill 会满是治不了病的规则。

**注意**：本项目的「skill」事实上就是 `prompts/base.md` + 场景叠加层（`family/budget/roadtrip/visa/safety`）
+ `.workbuddy/skills/travel-scene-planner/`。所以这个环在本项目里落地，
**等于对「场景叠加层」做配对评估驱动的迭代** —— 范围很清楚，不要扩散到重构代码。

### 「无 skill」必须定义精确

不能只说「no skill」，因为本服务**永远**会加载 `prompts/base.md`。三个条件要分开报数：

| 条件 | 给什么 | 用途 |
|---|---|---|
| ① 裸模型 | 只给 user message | 参考线，测「预训练知识本身够不够」 |
| ② 本服务默认 | base + 自动叠加层（无待评估 skill） | **基线** —— 配对对比的另一半 |
| ③ 带 seed skill | ② + 待评估 skill | **实验组** |

**要看的量是 ③ 相对 ② 的增量**，不是 ③ 的绝对值（SkillsBench 的 paired design）。
另外 ① 与 ② 的差，恰好回答你「成功的任务是不是预训练知识就够」那个问题。

### 任务级留出，不是运行级

optimizer 看过的任务，不能再出现在回归门里。按 **task_id 划分** train / holdout（建议 70/30），
否则第三轮之后所有数字都是自欺。

## 8. 隐私与偏差（先说清再采集）

1. **浏览器数据是隐私中的隐私** —— 浏览历史包含医疗、财务、身份、他人信息。
   采集前必须：本地处理、不入库原文、只留「场景标签」与脱敏后的任务描述、明确保留期。
2. **高频 ≠ 高价值**。高频需求之所以高频，往往正因为模型已经擅长它 —— 那部分正是你说「skill 可不涉及」的。
   真正的失败集中在**长尾**，而长尾在浏览历史里**天然欠采样**。
   → 出题阶段必须**主动加权低频场景**，不能只按频次排序。
3. **「用户做了什么」≠「用户该做什么」**。浏览历史里没有反事实：用户点进去 5 分钟就走了，
   是满意还是没找到？数据答不了。任务卡要把「可观测的行为」转成「可判分的终态」，这一步必然有推断，
   推断要留痕。
4. **对照组的伦理**：条件 ①②③ 必须用同一批任务、同一版本代码，否则比的是环境不是 skill。

## 9. 待定事项：3 条已实测确定，1 条仍待你定

**第 1 项「浏览器数据怎么进」已于 2026-09-28 实测定案，见 `research/SCENARIOS.md`。**
关键结论有三条，直接影响后续所有采集：

1. **不接 MCP，也不看个人浏览史** —— 改用「Google 公开搜索信号」：
   `suggestqueries`（Autocomplete，长尾 + relevance）为主，
   `trends/api/widgetdata/relatedsearches`（TOP/RISING）为辅。
   优点：不是某个人的历史，是**人群级的真实需求分布**，天然无隐私负担（原 §8 的顾虑基本解除）。
2. **Google Trends 对中文查询基本不可用**：16 个种子里 13 个返回空，daily RSS 已下线（404）。
   「data source = Google Trends」这句话在中文场景下会失效，**必须写清楚是 Autocomplete**。
3. **本机网络前提**：到 Google 域名直连 TCP 超时，需走本机代理 `127.0.0.1:7890`
   （另测 15000/54321/9080/50490/27036/7778 全不通）。硬多篇 False Negative 都出在这种地方。

**首轮采集结果**（636 条清洗后 query，详见 `research/SCENARIOS.md`）：
行程规划 28.1% / 签证手续 22.2% / 交通 12.6% / 时效事实 10.7% / 预算 7.5%；
**已覆盖目的地只占 17.1%**，最大缺口是当时的头号目的地（出境日本 124 次、东京 30 次，seed 里东京零条）。
该结论出自**旧出境主题的采集批次**：出境日本已于 2026-10-05 整块移除、主题收口为「外国人来华」，
覆盖率的分母已变，此行仅作历史记录，不要拿它判今天的知识缺口。

| # | 问题 | 选项 | 我的建议 | 状态 |

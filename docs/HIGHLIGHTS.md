# TripPal 项目特点说明

> 面向**评审者 / 接手者 / 融合方**：这份文档讲「这个项目**和一般的问答式旅行助手有什么不同**」。
> 它不是功能清单（那是 `docs/FEATURES.md`），也不是结构说明（那是 `docs/ARCHITECTURE.md`），
> 而是把散落在各处的**设计取舍**收拢成一组特点 —— 每一条都配「为什么这么做」和「这么做换来了什么」。

---

## 0. 三十秒读懂

| 项 | 内容 |
|---|---|
| 定位 | 给**来中国旅游的外国人**用的中文行程与事实助手（单垂直，主题已收口为「外国人来华」） |
| 出口 | 一句话进去，**永远是六种响应形态之一**（`clarify` / `plan` / `realtime` / `answer` / `guide` / `degraded`） |
| 主张 | 能排行程、能答**会变的事实**、能答**不会变的常识**；**答不了就明说答不了**，而不是编一个像答案的句子 |
| 技术底座 | FastAPI 单服务 + LangGraph 状态图（七节点主干 + 三条旁路）；LLM 走 OpenAI 兼容端点；向量库 memory / pgvector 双实现 |
| 规模 | `app/` 26 个文件 / 11153 行 · 知识库 **170 条** · 目的地词典 **68** · 提示词 8 份 · 测试 **678 全绿** |
| 最特别的一点 | **能在不调模型的地方绝不调模型**：意图、语言、槽位、排序、闸门、校验、**寒暄套话**全是确定性的 |

一句话概括它的性格：**确定性托底、模型只做生成、事实必须可溯源、查不到是一种合法产出。**

## 1. 定位：窄到只做一件事

大多数旅行助手做「全球出发地 → 全球目的地」的宽覆盖；这个项目**反过来收窄**：

- **只服务来华入境游客**，目的地收敛到中国的 68 个城市/地标；
- 覆盖的是外国人在华**最高频、也最容易踩坑**的四类场景：`family` / `budget` / `roadtrip` / `visa`，
  外加一个兜底层 `general`；
- **主动删掉了出境内容**（原日本线整块移除，种子 164 → 128 → 170 条）。

窄的收益不是「省事」，而是**可判分、可溯源、可收口**：知识库能逐条挂官方入口，
场景能逐条配必填槽位与工具白名单，评测能逐题写确定性断言。宽覆盖的助手做不到这些 ——
它的答案既验不了，也追不到源。

> 诚实标注：不做的部分也写清楚（无汇率换算、无真实票务、多副本需换共享存储），见第 14 节。

## 2. 特点一：出口只有六种形态 —— 答不了就明说

响应形态**本身就是产品设计**。它决定用户看到的是「行程」「事实」「常识」「追问」还是「答不了」，
而不是一坨看起来都差不多的自然语言。

| `type` | 什么时候出 | 关键字段 |
|---|---|---|
| `clarify` | 关键槽位缺（目的地 / 天数 / 预算 / 同行人） | `question`、`missing_slots`（**只问第一项，不四连问**） |
| `plan` | 信息够了 → 排行程 | `itinerary`、`route`、`citations`、`validation`、`checklist` |
| `realtime` | 问**会变**的事实（政策 / 开放时间 / 时刻 / 天气 / 交通） | `found`、`channels`（权威入口）、`unverified`、`expired_dropped` |
| `answer` | 问**不会变**的常识（「西湖有多大」） | `answer`、`confidence`、`hits`、`verify`（复核入口） |
| `guide` | 寒暄 / 致谢 / 元问题（「你好」「你是谁」「刚才我说了什么」） | `reply`、`starters` |
| `degraded` | 校验没过且回炉一次仍没过 | `reason`、`partial`、`validation` |

三条有意的约定：

1. **异常不抛 500** —— 链路内部出错退化成 `200 + type=degraded`，调用方必须判 `type`，不能只看 HTTP 状态；
2. **追问一次只问一件事** —— 缺四个槽位不是甩四个问题，而是按优先级问第一个；
3. **每种形态都有出路** —— 没有「查不到就返回空对象」这种半成品状态，查不到也装配成一条可读的答复。

## 3. 特点二：前门先分流 —— 「问事实」不再被当成「排行程」

这是项目**投入最多、也最像真产品**的一块。同一类错误反复出现，用户报过很多次：

> 输入「天安门什么时候升旗」，系统回的是「想去哪个城市？玩几天？预算多少？几个人？」
> —— 四个问题**全问错了方向**。用户没打算去哪玩，他问的是一个每天都会变的时刻。

现在的分法是**先分类、再决定走哪条路**，三条旁路**完全绕开** `classify/route/retrieve/generate/validate`：

```
一句话
 ├── 寒暄 / 致谢 / 元问题 ──────→ guide      不检索、不追问
 ├── 会变的实时事实 ────────────→ realtime   毫秒级，不经 LLM 生成
 ├── 不会变的常识 / 目的地咨询 ──→ knowledge  可给通用常识，但必须标注未核实
 └── 其余（排行程）────────────→ 主干五步
```

**为什么这算「特点」而不是「功能」**：判定是**确定性的**（正则骨架 + 让路规则，不调模型），
代价因此差了两个数量级：

| 路径 | 实测耗时 | 用不用模型 | 用不用向量 |
|---|---|---|---|
| 行程主干（真模型） | 20–60 s | ✅ 分类 + 生成 + 可能回炉 | ✅ |
| 实时事实旁路 | **6–28 ms** | ❌ | ❌ |
| 常识旁路 | **0.6–0.9 s** | ✅ 一次短调用 | ❌ |
| 缺槽短路 | ~0 ms | ❌ | ❌ |

两条让路规则保证旁路**不吞掉真请求**：① 命中触发词 **且** 本句没抽出任何行程槽位；
② 常识门额外一条件 —— 句中出现规划动词（「厦门怎么玩」）仍走主干。

此外，触发词**按问句骨架收，不逐词补**：有无 / 是非 / 列举 / 度量 / 时间 / 定义 / 咨询。
理由是这类问法无穷多（「是不是 X」「X 要不要预约」），逐词补必然再漏，而**每漏一次就是一次四连问**。

## 4. 特点三：确定性优先 —— 能不用模型的地方一律不用

这是全项目最一致的一条纪律。**模型只出现在它不可替代的地方**：

| 环节 | 谁来做 | 为什么不用模型 |
|---|---|---|
| 意图分流（行程 / 实时 / 常识 / 寒暄） | 正则骨架 | 同一句话两次跑出两种意图 = 不可调试 |
| 语言判定（zh/en/ja/ko） | 字符集 | 判定参与提示词装配，不能有随机性 |
| 槽位抽取（目的地/天数/预算/同行人/来源国） | 正则 + 词典 | 抽不到就是抽不到，不能「猜一个」 |
| 「相关条目」排序 | 词面 TF×IDF | 相似度永远返回 top_k，它不知道什么叫不相关 |
| 时效 / 相关性闸门 | 字段比对 | 过期就是过期，不该由模型酌情 |
| 校验（预算 / 事实 / 一致性） | 算术与引用比对 | 判分要能写成断言 |
| **场景分类 / 生成 / 常识作答 / 寒暄的 `meta`** | **模型** | 这些确实不可替代（问候/致谢/道别/取消/纯笑声是**封闭式套话**，已改定稿直答 —— 模型写的与定稿几乎逐字相同，却要等 0.9–11s） |

换来的是三样东西：**可复现**（同样的输入在离线假实现下走同一条路）、**可测试**（678 条断言钉住行为）、
**零成本**（判定与短路不花 token，也不受采样噪声影响）。

> 一个反例说明这条纪律的必要性：`ecnu-plus` 分类同一句「我们三个人去厦门 5 天，预算 8000」，
> 两次分别落在 `general` 与 `budget` —— **单次模型判定没有信息量**。所以凡是「判对判错要能追究」的环节，
> 一律不交给模型。

## 5. 特点四：事实必须可溯源 + 全层时效闸门

知识库里有**大量会过期**的内容：门票价、开放时间、签证政策、节假日安排、价格带。
所以规则是硬的：

- **每条条目三个时间字段**：`effective_date`（生效日）/ `fresh_until`（有效期至）/ `source`+`source_url`；
- **全层闸门**：**任何层**只要 `fresh_until < 今天` 一律丢弃、不参与排序、不进上下文
  （早期只对 `realtime` 层设闸门，理由是「常识不会过期」—— 这是错的，`general`/`scene` 里同样有票价与预约规则）；
- **丢弃不静默**：条数记进 `dropped_stale`（plan 链路）与 `expired_dropped`（realtime 链路）；
- **事实必须带 `citation_key`**：开放时间 / 门票 / 签证材料 / 交通耗时这类具体断言，找不到凭据就写「待核实」，**不编造**。

代价说清楚：**宁可这一条不进上下文（生成会退化成「待核实」），也不给一个看起来确定、实际陈旧的值。**

## 6. 特点五：把「诚实」做成看得见的产品特性

「答不了就明说」不只是文案，而是落到字段与像素上的：

| 做法 | 说明 |
|---|---|
| **`source_url` = 可点的官方核实入口**（不是原文出处） | 条目本身是官方文件 → 链接就是那个官方站点；条目是**编辑整理** → 链接指向该主题的官方入口（天气→中国气象局、铁路→12306、维权→12315） |
| **两种状态在界面上看得出区别** | 带 ↗ 的强调色 chip = 可点的官方入口；虚线压暗 chip = 编辑整理条目，hover 明说「无官方入口可点」。不这么分，用户点一下没反应只会以为坏了 |
| **权威入口名实一致** | `name` 必须描述**点击后落在哪儿**（承诺文档却链到首页 = 骗人）；`region` 写入口**实际覆盖的范围**（北京那条写成「中国」，杭州问开门也会拿到它 —— 给错地方比不给更坏） |
| **常识答案显式标注「未经本知识库核实」** + 给复核入口 | 给一条链接比替用户担保更诚实 |
| **「相关条目」不冒充答案** | 文案写明「不是这个问题的答案」—— 问「鼓浪屿有多大」命中的多是行程攻略，谈的是怎么玩 |
| **空缺就说空缺** | 地点解析不出来时只给通用入口；一条都没有就走「暂无已核实的权威入口」文案 |

**「查不到」在本项目里是一个合法产出**，不是失败。最坏的结果是那个中间态 —— 拿旧材料编一个看起来像答案的句子。

## 7. 特点六：业务规则与代码分离

**代码里不硬编码业务规则。** 所有编排参数收在 `routes.yaml` 一个文件、**11 节**：

| 节 | 作用 |
|---|---|
| `version_pin` | 版本钉，进响应体便于追溯 |
| `classifier` | 分类阈值（`clarify_below=0.45`、`soft_fusion_max=0.7`） |
| `fusion` | 场景叠加层优先级 `safety → visa → budget → scene` |
| `retrieval` | `top_k`、候选池倍数、三层配额与场景覆盖 |
| `tools` | 工具白名单（仅 3 个） |
| `guardrails` | 4 条护栏正文（中文是唯一真源，译文在 `i18n._GUARD`） |
| `scenes` | 5 个场景的关键词（含日 / 韩 / 英） |
| `intents` | 两条事实闸门的触发正则、允许类型、权威入口带覆盖地区 |
| `destinations` | 68 个目的地 + 多语言别名（含地标别名：天安门→北京、鼓浪屿→厦门） |
| `slot_extraction` | 日期 / 预算 / 同行人的四语言正则 |
| `prompts` | 提示词路径映射 |

**收益**：调阈值、加场景、补地名、收词表都不动代码；换业务域时**换的是内容不是逻辑**
（融合方甚至可以保留代码、只替换 `routes.yaml` + `seed/` + `prompts/`，就得到一个面向自己领域的问答系统）。

## 8. 特点七：可拆卸架构 —— 能只拿走一块

依赖方向**严格向下、无回环**，领域层**完全不知道 web 的存在**（实测：只 import 领域层时
`fastapi`、`langgraph` 都没被导入）。整套可替换性**收口在 5 个协议**上：

```
L3 装配层   main / graph / deps        ← 唯一注入点 deps.build_deps()
L2 领域层   slots intent knowledge realtime guide generate validate retrieve …
L1 适配层   llm(协议) embed(协议) store(协议) tools(协议) session
L0 底座     config schemas i18n pricing（零依赖纯函数）
```

按「想拿走多少」有四种拿法：

| 拿法 | 边界 | 你要接的线 |
|---|---|---|
| **A 整体挂载** | 整个 `app/` + `seed/` + `prompts/` + `routes.yaml` | 一个 `host.mount("/travel", create_app(deps))` |
| **B 只拿编排** | `graph` + `deps` + 领域层，不要 HTTP | 构造 `Deps`，调 `invoke/astream` |
| **C 拿单条链路** | 例如只要「实时事实」或「常识问答」 | 构造 2–3 个注入实现 |
| **D 拿单个模块** | 例如只要「中文口语槽位抽取」「多语言判定」 | **通常什么都不用接** |

**D 最值得一看**：`slots`（中文口语槽位）、`i18n`（多语言）、`pricing`（计价）、`intent`（意图四分流）
都是**零 web 依赖的纯函数**，`import` 即用，且都有测试。换实现的唯一入口是 `deps.build_deps()` 一个函数。

## 9. 特点八：中文口语槽位 + 「行程信息卡」双通道

口语的写法**枚举不完**。同一个意思可以说成「只有我一个人 / 就我一个成年人 / 我自己 / 1 位成人」，
正则补一轮漏一轮。更隐蔽的是**维度正交**：人数其实是 `数词 × 量词 × 身份词` 三个自由组合的维度，
靠加短语永远追不上 —— 曾经出现过「用户答『只有我一个成年人』不被识别、又问一遍」，
以及「没有老人也没有小孩」被**判成有长者同行**（比抽不到更糟：行程会错误加载长者节奏）。

所以留了**两条路**：

1. **抽取**（尽力而为）：把三个维度拆开做正交正则 + 否定按分句判；
2. **表单**（确定能通）：`POST /plan` 接受 `slot_overrides`，界面上的「行程信息卡」填了**直接落槽位、
   不经抽取、不靠识别**。它是抽不到时**唯一能通的路，不是装饰**（实测：一句里什么都没说、只填卡，也能直接出稿）。

优先级固定为 **本句 > 表单 > 会话历史** —— 本句最新最明确，表单是这一轮刚填的，会话里的只补前两者没说的部分。

## 10. 特点九：会话记忆与追问承接

问完「上海有没有免费的博物馆」，再问一句「那要预约吗？」—— 早期系统回的是四连问，
因为**每一句都被当成独立的一句**（会话历史只写不读）。现在承接靠**四个守卫同时成立**：

> 短（≤20 字）· 无已解析目的地 · 带疑问或属性提示 · 不含行程槽位与规划动词

任一不满足就不承接 —— **绝不吞掉新请求**（「那去上海玩三天」仍然是行程）。
承接的是上一轮的**事实主体 + 地点 + 判别性实词**（主体定检索作用域，实词定落到哪批条目）。

两条细节体现「不偷懒也不过度聪明」：

- **自带主体就不许被覆盖**：判据只有一条 —— 命中片段之前**切得出一个像样的主体吗**？
  「**华东师范大学**是不是有个新校区在那里」用自己切出来的；切不出（骨架在句首的「**是不是**还有一个校区」、
  占位名词「**具体位置**在哪儿」）才接上一轮；
- **元问题由历史确定性作答**：「刚才我说了什么」直接读轮次轨迹，**不调模型**（让模型看历史只会编）。

`GET /session/{id}` 把槽位 + 轮次轨迹 + 最近主体暴露出来，页面上有「会话记忆」面板；
每轮另落一行 JSONL 审计。**可见证据 > 口头保证。**

## 11. 特点十：多语言的三条边界

支持 `zh`（默认）/ `en` / `ja` / `ko`，边界写死在 `app/i18n.py` 模块 docstring 里：

| 边界 | 规定 | 为什么 |
|---|---|---|
| 检索查询 | **恒为中文** | 知识库是中文语料，检索跟着用户语言走会直接崩召回 |
| 用户可见输出 | 标题 / 行程 / 清单 / 建议 / 追问 → **跟用户语言** | 用户看不懂中文 |
| 开发期文案 | findings、日志、报错、测试断言 → **恒为中文** | 调试时不该还要在脑子里做一次翻译 |

再加一条：**引用不翻译** —— `citation_key`、来源原文、`source_url`、日期、金额一律保持原样
（翻了引用就断链）。所以英文请求的清单里，标签是英文、来源出处仍是中文。

跨语言的坑也踩过并修过：日语「2 名」量词即人数、「10 月 20 日」不带年被读成 20 天、
「3 万元の予算」谓语后置抽不到 —— **槽位抽取的语序与量词假设是按中文写死的**，
这类问题在纯中文测试里永远不出现。

## 12. 特点十一（研究线）：skill 进化闭环

除了产品本体，项目还带一条**方法论线**：从真实用户数据出题 → 在真实执行轨迹里迭代 skill →
**配对评估**决定留下什么。闭环分六步、四道闸，三个「承重关节」：

| 承重点 | 问题 | 定死的口径 |
|---|---|---|
| **A 谁判成败** | 单次成败没有信息量（采样噪声） | 主判必须**确定性 verifier**；每条任务跑 **≥3 次**记 `pass^k`；LLM judge 只兜底且要报人工抽查一致率 |
| **B 失败归因** | 只有 1/4 类失败属于 skill | 四分类：**数据缺 / 知识缺 / 能力缺 / 任务有病** —— 只有「知识缺」该写进 skill，其余写规则是白工甚至有害 |
| **C 剪枝 + 回归门** | 加规则的人永远比删规则的人多 | 语义去重 + 效用打分 + **删规则与加规则同优先级** + held-out 回归门 |

**三条被实测修正的假设**（有出处，不是设计偏好）：

- 模型**自产** skill 的平均增益 = **0**，人工策展的 **+16.6pp** → 「optimizer 自动写 skill」不能全自动；
- **加约束会掉分**：聚焦型（≤3 模块）**+18.9pp** vs 全面型 **+5.7pp**，85 个任务里 24 个变差 → 必须剪枝；
- **迭代搜索本身可以不必要**：带真实轨迹的**语料级统计反思**，单次离线 pass 就够，成本约 $1.60。

已实现为三个模块（A 需求出题 / B 执行评测 / C skill 优化），**178 条测试全绿**，真模型闭环已跑通。
它的价值在于：**把「我们的答案到底哪里不行」从感觉变成可归因的表。**

## 14. 与常见做法的差异（一页对照）

| 维度 | 常见做法 | 本项目 |
|---|---|---|
| 事实问题 | 一律走 RAG 生成 | **不走向量、不调模型**，直扫元数据 + 两道闸门，毫秒级 |
| 意图判定 | 交给模型（LLM 分类） | **确定性正则骨架**，可复现、可归因 |
| 时效 | 「这条信息可能过时」免责 | **过期条目直接丢弃并计数**，不给旧答案 |
| 查不到 | 返回通用兜底话术 / 空结果 | **「查不到」是合法产出**：给权威入口 + 名实一致 |
| 相关性 | 向量 top_k | **词面 TF×IDF + 相对截断**，没有就返回空（空是诚实的信息） |
| 知识缺口 | 让模型补 | **标注未核实 + 给复核入口**，时效性信息拒答 |
| 口语槽位抽不到 | 反复追问 | 加**表单直填通道**，抽不到也能走通 |
| 业务规则 | 散在代码里 | **`routes.yaml` 唯一真源**（11 节） |
| 复用 | 只能整体部署 | **L0/L1 模块可单独 import 拿走**，5 个协议可替换 |
| 评测 | 单次跑通即算对 | **≥3 次取 pass^k**，确定性 verifier，先校准噪声地板 |

## 15. 边界与已知不做的（诚实清单）

- **进程内状态**：会话与任务表只在当前 worker 内存里，`--workers > 1` 会漂移；横向扩需换共享存储；
- **融合形态未定**：跨进程 HTTP 还是同进程内嵌、会话 id 谁生成、鉴权层级 —— 见 `docs/API.md` §9；
- **汇率换算不做**：「5000 円 / 5000 원」只取数字；
- **工具只有 3 个**（`budget_sum` / `opening_hours` / `visa_policy`），模型不能自造工具；
- **语言硬保证**：模型不保证 100% 遵守语言段，未加「不符就重试」的后置检查；
- **意图骨架是有限集**：没被覆盖的新句式（如「今天股市怎么样」）仍会掉回行程链路 → 会被追问槽位；
  修法是加骨架正则，**不把意图判定改成调模型**（那会引入随机性）；
- **常识作答未经本库核实**：稳定常识风险低，但没有自动校验；
- **`source_url` 仍有缺口**：99 条来华条目里还有 48 条没有官方入口（编辑整理 / 价格测算类无单一原文页），
  补法是逐条找官方入口并**探测可达**，宁可没有，也不给一个点开对不上的链接。
